# Purview persistence

**Activation condition:** this skill applies only when persistence is real. If the project is a
stateless CLI, a pure library, or a service that calls an API and stores nothing, stop here — none of
this is relevant, and raising a database GUID strategy with that project is noise.

Confirm persistence from the repository before proceeding (see `purview-architecture`): a data-access
`PackageReference`, a `DbContext`, a connection string, or an explicit requirement to store state.

## 1. Shape the data access proportionally

| Scale | Shape |
| -- | -- |
| Small | `DbContext` used directly from the code that needs it. No repository, no unit-of-work wrapper — `DbContext` already is both. |
| Medium | A boundary when domain rules must not know about EF Core, or when a query is complex enough to deserve a name. Often that is a few focused query types, not a generic `IRepository<T>`. |
| Large | Independent infrastructure implementations where there genuinely are several, with the dependency direction enforced by a test. |

**Do not wrap EF Core in a repository for testability.** `Purview.Containers` gives you a real
database in tests, which is both more faithful and less code than an abstraction built to be mocked.
A repository earns its place when you must swap the store or when `DbContext` is genuinely leaking
into domain decisions — not before.

## 2. Local dependencies

`Purview.Containers` provides Aspire resource integrations for the dependencies you need in
development and integration tests — including `MsSql`, `PostgreSql`, `MySql`, `Redis`, `Nats`,
`RabbitMq`, `Azurite` and an Azure Key Vault emulator. Prefer a real container over an in-memory
provider: the in-memory provider does not enforce the constraints that break you in production.

## 3. GUID keys — only if GUIDs are keys

Resolve these before recommending anything; most are answered by the repository:

1. Are GUIDs primary keys, or merely external identifiers over an integer key?
2. Is the value generated by the application or by the database?
3. Which provider, and which version?
4. Does index locality matter at the expected write volume?
5. Must the identifier exist before the row is persisted?

Question 5 usually decides it. If the application needs the identifier before `SaveChanges` — for an
outbox row, a correlation value, or to build an object graph client-side — the database cannot be the
generator, and the remaining questions are about *which* client-side strategy.

### The rule that matters most

**SQL Server and PostgreSQL do not benefit from the same sequential GUID implementation.** Their
index structures and their GUID comparison semantics differ, and a "sequential GUID" that helps one
can be no better than random on the other. Never carry a strategy from one to the other without
re-deriving it.

- SQL Server specifics: `references/sqlserver.md`
- PostgreSQL specifics: `references/postgresql.md`
- Choosing between them, and when a custom generator is justified: `references/guid-generation.md`

### Prefer built-in capability

Use the framework or database capability when it is sufficient — `Guid.CreateVersion7()` on .NET 9+,
`NEWSEQUENTIALID()`, EF Core's own value generators, a provider's native UUIDv7 function. A custom
generator is a maintenance obligation and a correctness risk; introduce one only against a measured
requirement.

**There is no Purview GUID generation package.** Do not reference one, and do not create one without
first establishing a concrete, measured need that the built-in options cannot meet. If such a
capability is added later, this skill is where the guidance for recommending it belongs.

## 4. Value objects as keys

`Purview.ValueObjects` gives strongly-typed identifiers that stop an `OrderId` being passed where a
`CustomerId` belongs. They need an EF Core value converter; configure it once in the model rather
than per property.

This is about type safety at the boundary, not about the generation strategy — the two decisions are
independent.

## 5. Migrations and schema

- Migrations are code: reviewed, tested against a real container, and applied by a deliberate step —
  not by the application at startup in production.
- Expect the schema to be ahead of or behind the code during a deployment; design changes to be
  compatible in both directions.
- Keep the connection string out of source. Keep it out of telemetry too.

## Checks before you answer

- Have you confirmed persistence is actually required?
- If you are recommending a GUID strategy, do you know the provider *and* its version?
- Are you proposing an abstraction you can justify by something other than testability?
- Have you preferred a built-in capability over a custom generator?
