# Test Output Generation

This feature allows developers to inspect the generated source code during testing by writing all generated content to a dedicated folder.

## Usage

### Enable Output Generation

Set the environment variable `PURVIEW_TELEMETRY_OUTPUT_GENERATED_FILES=true` to enable output generation:

```bash
# Windows (Command Prompt)
set PURVIEW_TELEMETRY_OUTPUT_GENERATED_FILES=true

# Windows (PowerShell)
$env:PURVIEW_TELEMETRY_OUTPUT_GENERATED_FILES="true"

# macOS/Linux (Bash)
export PURVIEW_TELEMETRY_OUTPUT_GENERATED_FILES=true
```

### Customize Output Directory

By default, generated content is written to `generated-output/` relative to the test project directory. You can customize this location:

```bash
# Set custom output directory
export PURVIEW_TELEMETRY_OUTPUT_DIRECTORY="/path/to/your/output/directory"

# Or use a relative path
export PURVIEW_TELEMETRY_OUTPUT_DIRECTORY="./my-custom-output"
```

### Run Tests

With the environment variable set, run tests normally:

```bash
# Run all tests
make test

# Or run specific tests
dotnet test --filter "*MultiTarget*"

# Or run a specific test class
dotnet test --filter "TelemetrySourceGeneratorMultiTargetTests"
```

## Generated Content Structure

When enabled, each test generates a folder structure like this:

```
generated-output/
??? TestName/
    ??? README.md              # Summary and documentation
    ??? metadata.json          # Test run metadata
    ??? diagnostics.txt        # Compilation diagnostics (if any)
    ??? Generated/             # All generated source files
    ?   ??? SharedTypes.g.cs
    ?   ??? ActivityTypes.g.cs
    ?   ??? LoggingTypes.g.cs
    ?   ??? MetricTypes.g.cs
    ?   ??? MultiTargetGenerationTypes.g.cs
    ?   ??? Test.TestServiceCore.MultiTarget.g.cs
    ??? Input/                 # Input source files fed to generator
        ??? Input_000.cs
        ??? Input_001.cs
```

### File Descriptions

- **README.md**: Human-readable summary of the generation process
- **metadata.json**: Structured metadata including timestamps, counts, and environment info
- **diagnostics.txt**: Any compilation warnings or errors (only created if diagnostics exist)
- **Generated/**: Contains all files generated by the source generator
- **Input/**: Contains the input source code that was processed by the generator

## Example Usage

### Basic Example

```csharp
[Fact]
public async Task MyTest()
{
    const string source = """
        [assembly: Purview.Telemetry.EnableMultiTargetGeneration]
        
        namespace Test;
        
        [Purview.Telemetry.TelemetryGeneration]
        public partial interface IMyService
        {
            [Purview.Telemetry.Telemetry(GenerateActivity = true)]
            void DoSomething();
        }
        """;

    var result = await GenerateAsync(source);
    
    // Content automatically written to generated-output/MyTest/
    await TestHelpers.Verify(result);
}
```

### Accessing Output Information in Tests

```csharp
[Fact]
public async Task MyTestWithOutputInfo()
{
    // ... test setup ...
    
    var result = await GenerateAsync(source);
    
    if (TestOutputConfiguration.IsOutputEnabled)
    {
        testOutputHelper.WriteLine($"Output written to: {TestOutputConfiguration.OutputDirectory}");
        testOutputHelper.WriteLine($"Generated {result.DriverResult.Results.SelectMany(r => r.GeneratedSources).Count()} files");
    }
    
    await TestHelpers.Verify(result);
}
```

## Development Workflow

1. **Enable Output**: Set `PURVIEW_TELEMETRY_OUTPUT_GENERATED_FILES=true`
2. **Run Tests**: Execute the tests you want to inspect
3. **Examine Output**: Look in the `generated-output/` directory
4. **Inspect Generated Code**: Review the `.cs` files in the `Generated/` folder
5. **Check Diagnostics**: If there are issues, check `diagnostics.txt`
6. **Understand Input**: Compare with files in the `Input/` folder

## Benefits

- **Debugging**: Easily see what the generator produces
- **Development**: Inspect generated code during feature development
- **Troubleshooting**: Diagnose issues with generation logic
- **Learning**: Understand how different inputs produce different outputs
- **Documentation**: Generated README files provide context

## Performance Considerations

- Output generation adds minimal overhead when disabled (default)
- When enabled, it writes files to disk, which adds some test execution time
- The output directory is automatically cleaned between test runs
- Large test suites may generate significant disk usage when enabled

## Integration with CI/CD

This feature is designed for local development and debugging. In CI/CD environments:

- **Default Behavior**: Output generation is disabled by default
- **No Impact**: When disabled, there's no performance or storage impact
- **Optional CI Usage**: Can be enabled in CI for debugging specific test failures
- **Artifact Collection**: CI systems can collect the output directory as build artifacts if needed

## Git Integration

The output directories are automatically ignored by Git:
- `generated-output/` is ignored by default
- Custom output directories should be added to `.gitignore`
- The `.gitignore-additions` file in the test project shows recommended patterns

This ensures that generated test output doesn't accidentally get committed to source control.
